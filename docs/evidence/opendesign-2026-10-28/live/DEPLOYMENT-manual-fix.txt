What was wrong
--------------
The desktop client sends the model it has saved for a session with every
prompt. When the router had switched that session to something else, the
saved model was stale, so the next prompt switched the session back and the
host reported a model change the router did not make. The router read that
as the owner picking a model and suspended automatic routing.

The live evidence, from session ses_e9b57e9e (Adaptive polish checkpoint):
  10:19:43  deepseek -> glm     router-made (decision logged, stayed AUTO)
  10:56:29  glm -> deepseek     NOT router-made -> set MANUAL
  11:15:11  deepseek -> glm     NOT router-made -> set MANUAL again
The owner confirmed the picker was never touched.

The fix
-------
A change to a model the session has ALREADY been on is treated as the client
catching up with its saved selection: the model is recorded and automatic
routing stays on. Only a model the session has never used suspends routing,
which keeps a genuine pick working (the existing controller test for that
still passes). The set is seeded from the session's persisted model, so the
recognition survives a backend restart.

Also done at deploy time: the stuck session was returned to automatic
routing via the router's own resumeAuto command (manualOverride now false).
